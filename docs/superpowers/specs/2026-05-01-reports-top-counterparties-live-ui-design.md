# Reports Top Counterparties Live UI Design

**Дата:** 2026-05-01

**Статус:** draft for review

## Мета

Довести `top-counterparties` на екрані `Звіти` до завершеного live UI-сценарію, де блок не лише показує рейтинг або живе в Excel-export, а працює як операційний центр для поточного звіту. Клік по контрагенту має одразу фільтрувати та перебудовувати основну таблицю активної вкладки без переходу на інший екран.

## Обсяг

У межах цієї задачі змінюємо тільки канонічний Tauri + Svelte reports flow:

- `frontend/src/lib/screens/ReportsScreen.svelte`
- `frontend/src/lib/stores/reports.ts`
- `frontend/src/lib/types.ts`
- `frontend/src/lib/api.ts`
- `src/tauri_api/reports.rs`
- `src/db/reports.rs`
- пов'язані frontend/backend тести

Поза scope:

- окремий екран аналітики
- нові export-сценарії
- окрема навігація в картку контрагента
- порівняння двох періодів
- нові глобальні фільтри за межами reports screen

## Підсумковий UX

На екрані `Звіти` з'являється окрема картка `Топ контрагентів`, яка працює як керуючий блок для поточної вкладки. Вона показує список 5-8 контрагентів із сумою, вторинним контекстом і progress bar. Користувач бачить не просто топ, а може одним кліком звузити поточний зріз звіту до конкретного контрагента.

Сценарій користувача:

1. Відкриває `Звіти`.
2. Обирає вкладку: `bank`, `pnl`, `receivables` або `payables`.
3. Бачить рейтинг контрагентів саме для цієї вкладки.
4. Клікає по контрагенту в блоці `Топ контрагентів`.
5. Основна таблиця нижче перебудовується лише по цьому контрагенту.
6. Користувач бачить активний state `Фокус: <назва контрагента>`.
7. Повторний клік по активному рядку або кнопка `Скинути` повертає загальний зріз.

## Поведінка по вкладках

Рейтинг не є універсальним. Він залежить від активної вкладки:

- `bank` — топ за рухом грошей по контрагенту в межах вибраного періоду
- `receivables` — топ за сумою дебіторської заборгованості
- `payables` — топ за сумою кредиторки / очікуваних виплат
- `pnl` — топ за внеском контрагента у фінрезультат за період

Це правило є ключовим UX-рішенням: блок завжди відповідає поточному аналітичному сценарію, а не показує сторонню або статичну метрику.

## Drill-Down Model

У фільтрі reports screen додається `selectedCounterpartyId`. Це внутрішній state поточного звіту, а не глобальний app-level selection.

Поведінка:

- якщо `selectedCounterpartyId = null`, таблиця показує загальний зріз по поточних фільтрах
- якщо `selectedCounterpartyId` заданий, таблиця показує лише дані вибраного контрагента
- зміна вкладки скидає контрагентний drill-down, щоб не переносити фокус між різними аналітичними сценаріями
- зміна `dateFrom`, `dateTo`, `scope` або `query` також скидає `selectedCounterpartyId`, якщо вибраний контрагент може випадати з нового набору даних

## Важливий принцип рейтингу

Після кліку по контрагенту сам блок `Топ контрагентів` не звужується до одного рядка. Він продовжує показувати рейтинг для всього поточного зрізу вкладки, але активний рядок підсвічується.

Причина:

- блок має лишатись операційним центром
- користувач повинен мати змогу швидко перемикатись між контрагентами
- після drill-down рейтинг не повинен втрачати сенс

## API і Data Contract

Поточний `reports_load` лишається основною точкою входу. Окремий endpoint для `top-counterparties` не потрібен.

### Розширення filter DTO

У `ReportsFilterDto` додається:

- `selectedCounterpartyId: string | null`

### Розширення screen DTO

У `ReportsScreenDto` додаються:

- `topCounterparties: TopCounterpartyRowDto[]`
- `selectedCounterparty: { id: string; name: string } | null`

### Новий DTO для рейтингу

`TopCounterpartyRowDto` має містити:

- `counterpartyId: string`
- `counterpartyName: string`
- `primaryAmountStr: string`
- `secondaryLabel: string`
- `secondaryValue: string`
- `sharePercent: number`
- `isActive: boolean`

`sharePercent` потрібен для progress bar. `isActive` можна або віддавати з backend, або обчислювати у frontend; пріоритетно краще обчислювати у frontend від `selectedCounterpartyId`, щоб DTO не дублював derived state.

## Backend Design

`src/db/reports.rs` розширюється функціями для побудови топу контрагентів по кожній вкладці. Найкращий варіант — окремі loader-функції з єдиним shape результату, а не один гігантський SQL із розгалуженнями.

Пропонована модель:

- `load_top_counterparties_bank(...)`
- `load_top_counterparties_receivables(...)`
- `load_top_counterparties_payables(...)`
- `load_top_counterparties_pnl(...)`

Усі вони повертають спільний backend row struct, який потім мапиться у `TopCounterpartyRowDto`.

### Логіка агрегування

`bank`:

- джерело: `payments`
- групування: по `counterparty_id`
- метрика ранжування: найбільший рух за період
- secondary context: окремо `надходження` / `витрати` або `чистий рух`

`receivables`:

- джерело: відкриті `acts` + `invoices`
- групування: по `counterparty_id`
- метрика ранжування: сума до отримання
- secondary context: кількість відкритих документів або найбільша прострочка

`payables`:

- джерело: `payment_schedule` та інші невиконані платіжні зобов'язання, які вже використовує reports flow
- групування: по `counterparty_id`
- метрика ранжування: сума до оплати
- secondary context: найближча дата виплати або кількість прострочених позицій

`pnl`:

- джерело: документи, що формують дохід/витрати в поточному P&L
- групування: по `counterparty_id`
- метрика ранжування: внесок у фінрезультат
- secondary context: окремо дохід і витрати або net contribution

## Вплив selectedCounterpartyId на основні таблиці

Backend loaders основних таблиць приймають новий фільтр і враховують його:

- `load_bank_rows` — показує тільки операції вибраного контрагента
- `load_receivables_rows` — тільки документи вибраного контрагента
- `load_payables_rows` — тільки зобов'язання вибраного контрагента
- `load_pnl_rows` — тільки вклад вибраного контрагента

При цьому summary залишається узгодженим з таблицею. Тобто якщо є контрагентний drill-down, summary картки теж відображають звужений набір даних. Інакше користувач отримає конфлікт між KPI і таблицею.

## UI Layout

Блок `Топ контрагентів` додається в live layout reports screen як окрема картка поруч із фокус-картками та основною таблицею. Він не повинен виглядати як технічна таблиця або експортний preview.

Очікувана структура:

- header: `Топ контрагентів`
- subtitle: динамічний текст залежно від вкладки
- active state row: `Фокус: <назва>` + `Скинути`
- список рядків рейтингу
- empty state для періоду без даних

Кожен рядок містить:

- назву контрагента
- основну суму великим акцентом
- короткий secondary context
- horizontal progress bar
- активний hover/selected state

## Product Polish для reports screen

Окрім самого `top-counterparties`, у межах цього redesign-polish варто зробити три дрібні покращення, які не розширюють scope, але завершують сценарій:

- перемістити search ближче до фільтрів, бо це частина керування зрізом звіту
- понизити візуальний пріоритет export buttons відносно live-аналітики
- додати компактний текстовий context над таблицею на кшталт `Показано: дебіторка по контрагенту ...`

Ці зміни повинні залишитись локальними в межах `ReportsScreen.svelte` і не створювати нову дизайн-систему.

## Empty, Loading, Error States

Потрібні окремі продумані стани:

- якщо у вкладці немає даних взагалі, показуємо наявний empty state таблиці
- якщо таблиця має дані, але рейтинг для top-counterparties порожній, показуємо локальний empty state картки
- під час `reports.load(...)` весь screen оновлюється одним lifecycle, без окремого асинхронного loader для top-counterparties
- помилки лишаються на рівні поточного reports store

## Тестова стратегія

Frontend:

- оновити `ReportsScreen.test.ts` під новий блок і стани
- покрити клік по топ-контрагенту
- покрити повторний клік / `Скинути`
- покрити reset drill-down при зміні вкладки
- покрити динамічний subtitle і context text

Frontend store:

- перевірити, що `selectedCounterpartyId` коректно входить у `reports.load`
- перевірити, що зміна вкладки або фільтрів скидає drill-down

Backend/integration:

- тест на top-counterparties для `bank`
- тест на top-counterparties для `receivables`
- тест на top-counterparties для `payables`
- тест на top-counterparties для `pnl`
- тест, що `selectedCounterpartyId` реально звужує основні loaders

## Ризики і обмеження

- `pnl` drill-down по контрагенту може виявитися менш очевидним, якщо частина категорій зараз не асоціюється достатньо прозоро з контрагентом; це треба перевірити на існуючих query
- для записів без `counterparty_id` потрібно або ховати їх з топу, або показувати як `Без контрагента`; рішення має бути однаковим між `bank` і `payables`
- якщо query search вже фільтрує таблицю, top-counterparties теж має будуватись із тим самим query context, щоб screen не розходився сам із собою

## Критерії готовності

Функція вважається завершеною, коли:

- на reports screen є окремий polished блок `Топ контрагентів`
- блок змінюється по активній вкладці
- клік по контрагенту миттєво перебудовує основну таблицю
- active focus зрозуміло показаний і легко скидається
- рейтинг лишається повним even after selection
- summary, таблиця і context text узгоджені між собою
- frontend і backend тести покривають нову поведінку
