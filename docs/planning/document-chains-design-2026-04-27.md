# Document Chains Design

Оновлено: `2026-04-27`  
Статус: `draft for implementation`

## Навіщо цей документ

`doc_chain_load` і `doc_chain_create` уже присутні в UI contracts, але поки не є завершеним доменним сценарієм. Перш ніж реалізовувати код, треба зафіксувати мінімальні правила, щоб не побудувати випадкову логіку.

## Бізнес-ідея

Document chain — це послідовність пов’язаних документів навколо однієї господарської операції.

Базовий очікуваний ланцюг:

- `invoice`
- `act`
- `waybill`

Не кожен ланцюг мусить містити всі три документи, але UI має чесно показувати:

- що вже існує;
- чого ще не існує;
- що можна створити наступним кроком.

## Мінімальні правила для MVP

### 1. Canonical source document

Кожен chain view відкривається від конкретного `DocumentRef`.

Це означає:

- `doc_chain_load` приймає один документ;
- система визначає, які сусідні документи належать до того ж бізнес-ланцюга.

### 2. Напрям створення

Для MVP достатньо підтримати:

- створення дочірнього документа з поточного;
- prefill основних полів:
  - контрагент;
  - дата;
  - сума;
  - номер батьківського документа як reference;
  - позиції, якщо це дозволяє доменна модель.

### 3. Відображення відсутніх кроків

У `ChainStep`:

- `exists = true` означає, що документ уже є;
- `exists = false` означає, що можна запропонувати create action.

## Архітектурні рішення

### Рівень UI

UI повинен знати тільки view-модель:

- `ChainStep`
- `DocChainGroup`

UI не повинен визначати бізнес-правила самостійно.

### Рівень actions

У `src/actions/documents.rs` мають з’явитись сценарії:

- `load_chain(DocumentRef)`
- `start_chain_create(target_kind, source_ref)`
- `complete_chain_create(...)`

### Рівень DB / domain

Потрібно ухвалити одне з двох рішень:

1. Явний зв’язок між документами в БД.
2. Виведення зв’язку через поля reference / parent linkage.

Для довгострокової підтримки кращий шлях:

- явний зв’язок або стабільне посилання між документами.

## Питання, які треба закрити перед реалізацією

1. Чи може один invoice мати кілька act/waybill?
2. Чи може один act бути похідним від кількох invoice?
3. Де canonical parent link:
   - у дочірньому документі,
   - в окремій таблиці,
   - чи в обох місцях?
4. Які поля переносяться в prefill обов’язково?
5. Чи дозволяємо create chain для будь-якого статусу документа?

## Рекомендований MVP scope

Щоб не завалити першу реалізацію, достатньо такого:

- один parent document;
- один child per target kind;
- create from parent with prefilled counterparty/date/amount;
- read-only chain display;
- відкладене редагування chain relations поза MVP.

## Definition of Done

Document chains можна вважати реалізованими для MVP, коли:

- `doc_chain_load` показує реальний стан chain замість порожнього reset;
- `doc_chain_create` відкриває create flow з prefilled даними;
- зв’язок між документами зберігається передбачувано і повторно читається;
- є хоча б один integration test на chain creation/readback.
